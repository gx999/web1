# 연구소 v2 요구사항 재점검 (2026-11-10)

근거: 실제 세션 목록·예약 목록·원장 기록·코드, 공식 문서. [실제]=실행 기록 확인, [코드]=코드·모의시험만, [문서]=공식 문서, [미확인]=증거 없음.

## 1. 요구사항 대비 현재 구현

| 요구 | 현재 실제 모습 | 판정 |
|---|---|---|
| 연구원마다 독립 봇·세션 | 과제마다 **새 클라우드 세션**을 만들어 실행, 끝나면 idle. 지금까지 연구원 세션 13개(시험 A~F, P1 7단계) [실제] | 독립 세션은 충족. **상주 봇은 아님** |
| 계속 살아서 과제를 기다림 | 기다리는 프로세스 없음. 필요할 때 생성→종료 [실제] | **불일치** |
| 동시 작업 | 2개 동시 실행 2회 확인(A/B, C/D) [실제]. 코드 상한 2 [코드]. 플랫폼 동시 세션 상한은 비공개 [문서] | 일부 충족(2명까지 확인) |
| 끝나면 다음 연구원에게 자동 인계 | P1에서 7단계 인계가 실제로 일어남. 단, 인계 판단·다음 세션 생성은 **이 대화 세션(관리자 역할의 Claude)이 연구원 완료 메시지에 깨어나 수행** [실제] | 사용자 재실행 불필요는 맞음. 그러나 **독립 관리자 시스템이 아니라 사람이 지켜보는 대화 세션이 관리자** |
| 관리자를 누가 언제 깨우나 | 현재: 연구원 `send_message`가 이 세션을 깨움. 관리자 예약은 **0건** [실제]. `tools/manager_run.py`는 작성·모의시험만 [코드] | 무인 관리자 **미배포** |
| 수집→초안→검토→수정 자동 연결 | P1에서 실제 연결(수정 2회, 재검토 승인) — **사람 감독 시범** [실제]. 무인 연결 [미확인] | 부분 |
| 한 연구원·출처가 막혀도 계속 | 대법원 접근 거부·외부 출처 한도에도 다른 출처·과제 계속 [실제] | 충족(감독 하) |
| 맥 꺼져도 운영 | 모든 연구원은 클라우드 컨테이너에서 실행 [실제]. **맥 전원 종료 상태 시험은 하지 않음** [미확인] | 미확인 |
| 지피의 지시·조회·보고 | Notion 읽기·쓰기(사람 있음·예약 실행), 비공개 GitHub 읽기 [실제]. 지시함→처리→기록 1회는 관리자 수동 실행 [실제]. 지피의 status 읽기 보고 [미확인] | 부분 |

## 2. 실제 구성도 (현재)

```text
사용자 ─ 대화 ─▶ [이 Claude 대화 세션 = 관리자 역할, 사람이 지켜봄]
                     │ create_session                ▲ send_message(완료·체크포인트)
                     ▼                               │
             [연구원 세션들: 과제마다 생성 → 종료(idle)]──┘
                     │ (P1) 결과 → 관리자가 기록
                     ▼
   Notion: 작업 대기열(시험)·지시함·비공개 원고 사본      GitHub 비공개 daeyong-lab: 공식 원장(P1 이전 완료)
   지피(ChatGPT): Notion 읽기·쓰기, GitHub 읽기 ──────▶ (연결은 확인, 운영 루프는 1회 수동)
   홈페이지 /lab/: 아직 기존 ChatGPT 연구소 상태 서버에 연결 — v2와 무관
```
예약 사이: 예약 자체가 없으므로, 이 대화 세션이 깨어 있지 않으면 **아무 일도 일어나지 않는다**.

## 3. 세 방식 비교

| 항목 | ① 상주 봇 | ② 이벤트형 작업자 | ③ 정시 예약 |
|---|---|---|---|
| 과제 없을 때 | 프로세스는 대기(추론 비용 없음, 서버 운영비) | 아무것도 실행 안 됨 | 매 정시 짧게 깨어 확인 |
| 시작 지연 | 수 초 | 이벤트 후 세션 기동(수십 초~분, [미확인] 실측 필요) | 최대 1시간 |
| 동시성 | 서버 자원·API 한도만큼 | 플랫폼 동시 세션 상한(비공개)·이벤트 시간당 상한 | 같음 |
| 장애 복구 | 프로세스 감시·재시작 필요 | 원장 기반 재개(구현됨 [코드]) | 다음 정시에 회수 |
| 모델 사용량 | API 종량제(별도 과금) | 구독 사용량 | 구독 사용량 |
| 맥 의존 | 서버 위치에 따라 | 없음(클라우드) | 없음 |
| 이 계정에서 지금 가능? | 별도 서버+API 키 필요 → **승인 전 불가** | **가능**(Claude 예약의 GitHub 이벤트 트리거·세션 간 `fire_trigger`) — 미구축 | 가능 — 미생성 |

**현재 구현은 ②의 형태를 사람이 지켜보는 대화 세션이 관리자로서 수행한 것이며, ①이 아니다.** 시간당 예약만으로는 ③이다.

## 4. 모델 혼합(Claude·ChatGPT·Gemini)

| 서비스 | 구독 안의 자동 실행 | 확인된 제한 [문서] | 이 계정 실사용 |
|---|---|---|---|
| Claude Code 클라우드 | 예약·GitHub 이벤트·API 실행, 세션 간 생성·메시지 | 예약 최소 1시간, 시작 시간당 상한(예약 100/계정, 실행·API 30/과제), 이벤트 시간당 상한, 동시 세션 상한 비공개, **구독 사용량 소모 — 사용 크레딧 켜져 있으면 초과분 과금** | 세션 생성·메시지·푸시 [실제] / 예약 [미확인] |
| ChatGPT(지피) | 예약 작업(Pro 활성 15개, 1시간 이상 간격, 웹훅 없음), 앱 연결 | 같음 | Notion 읽기·쓰기, GitHub 읽기 [실제]. GitHub 쓰기·연구 수행 [미확인](기존 연구소 기록상 연구 예약 운영 이력 있음) |
| Gemini(Jules) | Google AI Pro에 포함 시 비동기 작업(일 100, 동시 15), GitHub 저장소 대상 | 같음(공식 한도 페이지) | **가입·연결 [미확인]**. 법학 자료 조사 적합성·인터넷 접근 [미확인] |
| 각 회사 API | 서버에서 상시 호출 가능 | 종량 과금 | OpenAI API 잔액 0(기존 기록). 신규 키·결제는 승인 필요 |

독립성: 같은 모델의 다른 세션 = 문맥 분리(앞선 의견을 못 봄)지만 같은 성향의 오류가 겹칠 수 있음. 다른 모델 = 학습·추론 방식이 달라 교차 검증 가치가 더 큼. 둘 다 정확성 보증은 아니며 원문 대조가 기준.

구독 인증을 외부 서버에 복제하는 방식은 쓰지 않는다. 외부 서버가 구독을 '공식적으로' 받아 작업을 맡기는 경로는 이번 확인 범위에서 찾지 못했다 [미확인].

## 5. 비용 관점
- **추가 비용 없는 최선(②):** Claude 예약(GitHub 이벤트 + 1시간 안전 주기 + 연구원 완료 시 즉시 호출) + 지피 예약 작업(교차 검토) + (가입돼 있다면) Jules. 한계: 상주 아님, 기동 지연, 구독 사용량 창 소진 시 대기, 시간당 시작 상한, 동시 세션 상한 비공개.
- **비용이 드는 구조(①):** 상시 서버(호스팅비) + 각 모델 API(종량) + 비밀값 보관. 금액은 사용량에 따라 달라 지금 산정하지 않는다.
- **선결 확인:** claude.ai/settings/usage 의 **사용 크레딧(usage credits) 꺼짐** — 켜져 있으면 한도 초과분이 종량 과금된다(문서).

## 6. 권장안
**② 이벤트형 + 모델 혼합 검토.**
1. Claude 관리자 예약 1개에 트리거 3종: (a) 비공개 저장소 Issue 이벤트(지피·사용자의 지시, 연구원 완료 알림), (b) 연구원이 끝나며 `fire_trigger`로 즉시 호출, (c) 1시간 안전 주기(누락 회수).
2. 연구원은 과제마다 새 세션(현행 유지), 결과는 `results/`에만, 관리자가 원장 반영 — 끊기지 않는 단계 연결.
3. 독립 검토 한 단계를 지피(ChatGPT 예약)가 맡는 교차 모델 검토를 시험. Jules는 가입 확인 후 선택.
이유: 과제가 없으면 비용 없이 쉬고, 과제가 들어오면 분 단위로 스스로 시작하며, 맥·이 대화와 무관하다. ①과의 차이(상주 프로세스 아님, 기동 지연, 한도)는 남는다.

## 7. 개발 단계와 검증 기준
| 단계 | 내용 | 통과 기준 |
|---|---|---|
| 0 | 사용 크레딧 꺼짐 사용자 확인 | 확인 전 예약 생성 없음 |
| 1 | 관리자 예약 생성(24시간 한정, 종료 장치 3중) + `fire_trigger` 연쇄 | 연구원 완료 후 관리자 자동 기동, 사람 개입 0회 |
| 2 | 비공개 저장소 Issue 이벤트 트리거(웹 화면에서 사용자 설정 필요) | 지피가 이슈를 만들면 수 분 내 과제 등록 |
| 3 | 24시간 시험(T24A 정상·T24B 실패 격리) | 단계 연결·검토·수정 무인 완료, 중복 0, 화면=원장 |
| 4 | 맥 종료 구간 실측 | 사용자가 알려 준 종료 구간에 실행 기록 존재 |
| 5 | 지피 교차 검토 1건 | 지피가 GitHub에서 검토 패킷을 읽고 결과 기록 |
| 6 | 홈페이지 공개 상태 전달(승인 후) | 허용 필드만, 원장과 일치 |

## 24시간 시험 계획에 주는 영향
아직 시작 전(예약 0건). 시간당 예약만으로는 ③만 시험하게 되므로, 계획을 **②(완료 시 즉시 호출 + 1시간 안전 주기)**로 바꿔 시험하는 것을 권장한다. 이 경우 같은 24시간 동안 실행 횟수가 늘어 구독 사용량을 더 쓴다. 시간당 시험이 성공해도 ① 요구 충족으로 보고하지 않는다.
