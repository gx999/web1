### 상주 프로세스 / 이벤트 기반 / 정기 예약 비교

| 방식 | 이 환경에서 | 장점 | 공백 |
|---|---|---|---|
| 상주 프로세스 | **불가** (컨테이너 유휴 회수) | — | 24시간 연속 연산은 구독만으로 보장 불가 |
| 이벤트 기반 작업자 | **가능** — 작업자가 끝나면 관리 예약을 즉시 호출(`fire_trigger`) 하거나 다음 세션 생성 | 단계 간 지연 거의 없음, 독립 과제 병렬 | 첫 시동이 필요. 사슬이 끊기면 예약이 복구 |
| 정기 예약 | **가능** — 최소 1시간 간격, 매번 새 세션 | 맥 꺼져도 동작, 끊긴 사슬 복구 | 최대 1시간 지연. 사용량 한도 시 대기 |

**권장:** 이벤트 기반 사슬 + 1시간 간격 관리 예약(복구·한도 재확인용) 병행. 사용자가 원한 '상주 연구소'와의 차이: 연구원은 *계속 살아 있는* 프로세스가 아니라 *과제가 있을 때마다 새로 뜨는* 독립 세션이며, 구독 사용량 한도(5시간 창 등)에 도달하면 '한도 대기'로 멈춘다. 목표를 축소하지 않고 이 공백을 그대로 보고한다.

## 3. 지피(ChatGPT)와 연구소의 연결 — 확인 결과와 후보

Claude Code에서 쓸 수 있다고 지피에게도 연결된다고 가정하지 않았다. **나는 ChatGPT 계정에 접근할 수 없으므로 지피 쪽 연결은 아래 시험을 지피가 실제로 해야 확인된다.**

| 후보 | 지피 측 근거 | Claude 연구원 측 | 판단 |
|---|---|---|---|
| A. 기존 ChatGPT Sites 연구소 MCP | **[사용자 기록상 실제]** 지피가 과제 생성·조회·검토 기록, 예약 실행에서 사용 | 해당 서버 HTTP 호출에 소유자 범위 토큰 필요(새 인증정보 → 승인), 호스트 허용 필요. 서버 코드 미확인 | 지피 연결은 이미 검증된 유일한 경로. 다만 기존 서비스 변경(승인 필요) |
| B. Notion 공유 원장 | ChatGPT Notion 플러그인이 쓰기 가능하나 **변경마다 승인 카드**가 뜬다는 최근 보고 [[xray.tech](https://www.xray.tech/post/connect-chatgpt-notion)] — 예약 실행에서는 승인 불가 가능성 | 읽기 OK, **쓰기는 승인 필요로 실제 멈춤** | 사람이 있을 때의 조회·지시용으로만 적합. 무인 원장으로는 양쪽 모두 승인 장벽 |
| C. 새 연구소 원장 서버(MCP+HTTP) | ChatGPT 개발자 모드 사용자 MCP는 쓰기 도구 지원, 기본 확인 절차 있음 [[OpenAI](https://developers.openai.com/api/docs/guides/custom-mcp-server)], OAuth 또는 무인증만 지원 보고 | Bash에서 HTTP 호출 + 프록시 주입 토큰(채팅 노출 없음) → MCP 승인 장벽 없음 | 무인 운영에 가장 적합. 단 새 호스팅·인증정보 → 승인 필요(무료 등급 후보) |

**알림:** 현 플랫폼에서 연구소가 지피에게 푸시할 공식 경로는 확인되지 않았다. 지피는 ChatGPT 예약 작업이나 사용자 요청 때 **조회**해야 한다. 지피가 Claude 연구원을 직접 깨우는 경로도 없다 → 지피가 원장에 과제를 등록하면 Claude 관리 예약(≤1시간)이 인수한다.

### 지피에게 확인을 요청할 시험 (사용자가 ChatGPT에서 실행)
1. 지피 설정 → 연결된 앱/플러그인 목록에 기존 연구소 MCP와 Notion이 있는지, 도구 이름 목록.
2. 지피에게: "Notion '작업 대기열 (시험)'을 조회하고 과제ID `G-1-지피등록-시험` 행을 queued로 추가해" → 승인 카드 여부 기록.
3. ChatGPT 예약 작업 1회로 같은 조회를 시켜 예약 실행에서도 되는지 확인(승인 카드가 필요하면 실패로 기록).
결과를 알려주시면 연결 방식을 확정한다. 그 전에는 '연결 완료'로 표시하지 않는다.

## 4. 역할 분담과 승인 경계 (추가 지시 반영)

- **사용자:** 연구 방향·우선순위, 중요한 결정, 공개·투고·외부 전송·비용·권한 승인.
- **지피(운영총괄):** 원장 조회, 승인 범위 안 과제 등록·우선순위 조정·배정 요청·재시도 요청, 결과 종합 보고. **승인 대상 행동은 '승인 요청' 기록만 만들 수 있다.**
- **연구 관리자(결정론적 코드, Claude 예약/이벤트로 실행):** 배정·임대·재시도·한도 대기·다음 단계 자동 생성·독립 검토 연결. 연구 판단은 하지 않는다.
- **독립 연구원:** 과제마다 새 Claude 세션. 자료수집·논점·초안·독립검토·데이터검증.
- **Claude Code(이 세션):** 시스템 설계·구현·시험·오류 수정·문서화.

**승인 우회 방지:** 지피와 사용자가 같은 계정·커넥터를 쓰면 원장 기록만으로는 '사용자 승인'과 '지피 기록'을 기술적으로 구분할 수 없다. 따라서 공개·투고·외부 전송·비용·권한 변경은 **자동 실행 경로에서 제거**하고, 사용자가 직접 응답하는 승인 화면(Claude 앱 승인 카드 또는 사용자 본인 지시)에서만 실행한다.

```text
사용자 ──자연어──▶ 지피(ChatGPT) ──조회·과제등록·승인요청──▶ [연구소 원장] ◀── 공개 투영(허용 필드만) ──▶ daeyongjeong.com/lab
   │                                                  ▲   │
   │ 승인(직접)                                        │   │ 과제·체크포인트·출처·판본·검토
   ▼                                                  │   ▼
Claude 승인 카드 ◀─ 승인대상 작업만 ─ 연구 관리자 tick (1시간 예약 + 완료 이벤트) ── create_session ──▶ 독립 연구원 세션들
```

## 6. 구현한 것 (이 세션, 격리 디렉터리 `lab-v2/`)

- `kernel/model.py` 상태·단계·오류분류·출처 상태(원문확보/검색만/접근제한/일시실패), 문서 날짜 종류 구분.

- `kernel/projection.py` 허용 목록 공개 투영(제목·질문·원고·URL·세션ID 구조적 배제, 시험 과제 제외), 상태 전송 재시도, 오래된 정보 '확인 지연' 표시.
- `tests/test_kernel.py` **[모의] 16개 통과**: 전 단계 연결·수정·재검토, 일부 출처 실패, 중단 재개, 실행 중 중복 방지, 늦은·중복 완료, CAS 충돌, 한도 대기, 한 과제 차단 중 다른 프로젝트 진행, 재시도 상한, 실행 생성 실패, 독립성 규칙, 공개 정보 차단, 전송 실패 재전송, 재시작 후 원장 보존.

## 8. 결정이 필요한 지점 (승인 요청)

1. **원장 위치·지피 연결 방식** — A(기존 Sites MCP 확장) / C(새 원장 서버, 무료 등급) 중 선택. 지피 측 시험(3절) 결과 필요.
2. **무인 쓰기 권한** — (a) claude.ai 커넥터 설정에서 Notion 쓰기 도구 '항상 허용' 또는 (b) HTTP 원장 + 범위 제한 토큰(`request_credential`, 프록시 주입). 권장 (b).
3. **관리 예약 생성** — 1시간 간격, 매번 새 세션. 사용량은 구독 내, 한도 시 대기.
4. **비공개 저장소** — 원고·출처 추출문 보관용(예: 비공개 `daeyong-lab`). 사용자가 만들어 이 세션에 추가.
5. **원격 푸시** — 이 `lab-v2/` 코드(개인정보 없음)를 공개 저장소 `gx999/web1`의 작업 브랜치에 올려도 되는지. 올리지 않으면 컨테이너 회수 시 사라짐.
6. **홈페이지** — 원본 소스는 맥(Drive 사본)에 있고 Firebase 배포 인증정보가 이 환경에 없다. 실행 기반 검증 후 `/lab/` 개편안을 만들고, 배포는 승인·인증 방식 결정 후 진행.

## 9. 다음 단계 (승인 후)

1. 지피 측 연결 시험 결과 반영 → 원장 확정.
2. 실제 과제 1건(첫 분야: 사이버침해사고 대응의 제도·법적 문제)을 수집 → 초안 → 독립 검토 → 수정까지 실제 세션으로 연결.
3. 실제 장애 시험: 출처 실패(대법원 사이트 실제 차단 상황 활용), 작업 중단, 중복 실행, 한도 도달, 상태 전송 실패, 맥 꺼진 기간.
4. 현황판과 실제 기록 대조 → 홈페이지 `/lab/` 개편.
5. 안정 후 연구원 수 확대, 기존 자료 이전·전환 계획 제시.
